# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Development (local, no Docker)
```bash
# Activate venv
source venv/bin/activate

# Run API server (dev mode, port 8001)
uvicorn api.main:app --host 0.0.0.0 --port 8001 --reload

# Run tests (pytest.ini sets asyncio_mode=auto + testpaths=tests, so bare `pytest` works from root)
pytest                                   # Full suite (async tests auto-detected)
pytest tests/unit/ -v                    # Unit tests (no services needed)
pytest tests/integration/ -v             # Integration tests (mocked)
pytest tests/unit/test_gis_processor.py  # Single test file
pytest --cov --cov-report=term-missing   # With coverage (matches CI)
```

> CI (`.github/workflows/ci.yml`) runs `pytest --cov` on Python 3.12 for every push/PR to `main`. It installs only `requirements.txt` and does **not** stand up Postgres/Redis/Ollama, so tests must pass without live services (unit + mocked integration only).

### Docker (production-like, port 8000)
```bash
docker compose up -d          # Start all services
docker compose logs -f api    # Follow API logs
docker compose restart api    # Restart after code changes
```

### Pull Ollama model (one-time setup)
```bash
./scripts/pull_model.sh
```

## Architecture

The system is a **multi-agent AI platform**, first applied to mining & GIS intelligence but not hard-wired to that domain at the architecture level (see `docs/PROGRESS.md` and the v5 evolution blueprint for the domain-generalization plan). This section was rewritten 2026-07-16 after an audit found it had drifted — it previously described only 9 of 17 live routers and omitted entire subsystems (`orchestrator/`, `agents/`, `memory/`, `rag/`, `workspace/`, `telemetry/`, `messaging/`, `mcp_client/`/`mcp_server/`, `plugins/`, `scheduler/`) that are real, tested, and load-bearing. **Verify against actual code before trusting any doc, including this one** — that same audit also found and corrected a stale docstring in `security/auth.py` making an incorrect claim about its own file.

"router-level" = `dependencies=[Depends(get_current_principal)]` on the `app.include_router(...)` call itself, so a future endpoint added under that prefix can't ship unauthenticated by omission (added Fase 1, after these 5 routers were found to have no auth dependency at all). Everywhere else, auth is opt-in per-route inside the router file — grep for `Depends(get_current_principal)` before assuming a route is protected. `API_KEYS` being blank (current dev default) makes every checked route treat the caller as admin; this deployment relies on loopback-only network binding (`docker-compose.yml`, `ai-engine.service`) as its actual isolation, not API keys — a documented trade-off, not an oversight.

Configuration lives in `api/config.py` (pydantic-settings); most defaults have moved to `config/*.yaml` (Configuration Center, versioned), with `.env` for secrets and per-deployment overrides.

> **Three agent execution paths exist side by side — know which one you're touching:**
> - `core/chat/` (§9) — **primary user-facing feature**. LLM-driven native tool-calling via Ollama `/api/chat`, backs the `/` web UI.
> - `orchestrator/` + `agents/` + `registry/` (§2) — **15-role multi-agent system**, backs `/api/v1/orchestrator/*` and the Workflow UI page.
> - `agent/` singular (§3) — **older rule-based planner**, kept only for `/api/v1/agent/run`. Don't extend it without a specific reason to.
>
> All three call into the same `agent/tools/registry.py` (`ToolRegistry`) for actual tool execution. **Fase 6 (Cowork Experience) bridges the first two**: the chat tool `run_orchestrated_workflow` (`agent/tools/orchestrator_tools.py`) lets a Chat Engine turn trigger a real Orchestrator run — see §9's Fase 6 note. The rule-based `agent/` path (§3) is not bridged.
>
> Experimental "enhanced" code that was never wired up is archived at `backups/archived_20260602/` (`core_enhanced.py`, `toolkit.py`, `agent_enhanced.py`, `logger_enhanced.py`, `skills/`). Don't resurrect it without reason.

### 2. Orchestrator & Multi-Agent System (`orchestrator/`, `agents/`, `registry/`, `workflows/`)
- `orchestrator/planner.py` + `execution_graph.py` — builds a DAG-based plan from a goal; does not execute it.
- `orchestrator/dispatcher.py` + `task_manager.py` — executes the DAG. State machine has real transitions beyond the happy path: `PENDING→PLANNING→RESEARCH→EXECUTING→REVIEWING→APPROVED→COMPLETED`, plus `CANCELLED`/`FAILED`/`RETRY`/`ROLLBACK` (including a retry loop back to `PENDING`); illegal transitions raise `IllegalTransitionError` rather than silently corrupting state.
- `orchestrator/routing_engine.py` — picks provider/model per step.
- `agents/generic_agent.py` — **all 15 roles (planner/research/analyst/writer/reviewer/memory/guardrail/prompt_optimizer/tool/vision/reflection/critic/consensus/cost_optimizer/confidence) are still one class, `GenericLLMAgent`, configured with a different prompt per instance** — Fase 2 deliberately did not split this into subclasses (regression risk against 685+ tests for a benefit the guard below already delivers). `agents/capabilities.py` classifies each role into `AgentCapability.{SPECIALIST,EXECUTOR,VALIDATOR}` (every `BaseAgent` subclass gets `.capability` for free, derived from `.role` — no override needed) and `agents/validation_guard.py::assert_independent_validator` enforces "builder ≠ validator" wherever a `Task.metadata["validates_agent_ids"]` marks it as judging another agent's output — checked in `orchestrator/dispatcher.py::dispatch()`, the shared chokepoint. **Scope of what's actually closed**: only `orchestrator/consensus.py::ConsensusEngine.arbitrate()` sets that metadata today (confirmed by grep — the only real code path that dispatches an agent to judge another's output), so the guard currently protects consensus arbitration only. `orchestrator/reflection.py`'s self-evaluate/revise loop is untouched by design — it re-dispatches the *same* role, scored algorithmically (`ConfidenceScorer`), not judged by another agent, and already escalates to Human Approval on low confidence; that's a separate, larger design question, not bundled into this pass. Don't assume every "reviewer"/"critic" task is independence-checked — only ones that explicitly set `validates_agent_ids`.
- `registry/agent_registry.py` — the 15-role registry (Agent Manager equivalent). `registry/` also holds the provider registry and plugin registry.
- `workflows/` — five orchestration patterns: `sequential.py`, `parallel.py`, `reflection.py` (self-critique), `voting.py`, `consensus.py`, `approval.py`. `HumanApprovalGate` in `approval.py` never auto-decides and audit-logs every decision with approver identity + reason, but by design has no notion of *who* the caller is — RBAC-gating who may call `decide()` is the caller's job (`Orchestrator.finalize_approval`), not enforced inside the gate itself.
- `orchestrator/orchestrator.py::get_shared_orchestrator()` — process-wide `Orchestrator` singleton (Fase 6). `api/routes/orchestrator.py` (Workflow/Approval UI pages) **and** `agent/tools/orchestrator_tools.py` (the chat bridge, §9) both use this ONE instance — otherwise a Human Approval request opened by a chat-triggered run would live in a `TaskManager`/`HumanApprovalGate` the Approval page's own instance never sees, for the in-memory (dev/CI default) state backends. Lives here, not in `api/routes/`, specifically so `agent/tools/` never has to import from `api/` (the dependency direction it avoids everywhere else — see `agent/tools/workspace_reader.py`).

### 3. Legacy Rule-Based Agent (`agent/`)
`agent/core.py` — `AIAgent` runs a deterministic plan→execute→evaluate loop (max 8 steps). The planner is **rule-based** (`_smart_plan`), not LLM-driven, to avoid hallucination; LLM planning (`_plan`) is a fallback only. As of Fase 1, input runs through `security.prompt_guard` (can block outright, unlike the streaming chat path) and PII redaction, and output is validated/redacted before returning — added alongside the equivalent wiring in `core/chat/engine.py` (§9); see §8 for how these differ between the two paths.

All agent capabilities (from all three paths in §1) go through `agent/tools/registry.py` (`ToolRegistry`). Tools are registered with `registry.register(name, fn, description, extensions)`. The `auto_reader()` method maps file extensions to reader tools automatically.

Tool categories:
- `agent/tools/readers.py` — read_pdf, read_txt, read_docx, read_csv, read_json, read_image, read_xlsx, read_pptx (xlsx/pptx: Workspace Slice 3, Fase 12)
- `agent/tools/writers.py` — write_pdf, write_docx, write_html, write_txt, write_json, write_xlsx, write_pptx
- `agent/tools/analyzers.py` — analyze_text (wraps Ollama), generate_code
- `agent/tools/gis_io.py` — read_geojson/read_shp, write_geojson/write_shp, convert_geo (KML↔GeoJSON↔SHP via `fiona`/`shapely`; reuses `core/gis/processor.py` for the math)
- `agent/tools/images.py` — image_convert/resize/crop/rotate/compress, images_to_pdf (Pillow). **Transform only — no image generation** (a local text LLM can't synthesize images)
- `agent/tools/workspace_reader.py` — reads from `workspace/`-registered folders (§7)
- `agent/tools/memory_tools.py` — `remember_fact`/`recall_facts`, cross-session memory namespaced by owner (Fase 3, §5)
- GIS area tools registered inline in `build_registry()` using `core/gis/processor.py`

**To add a new agent tool:** implement the function, call `registry.register(...)` in `agent/tools/registry.py:build_registry()`, and — if the chat engine should be able to call it — add its JSON schema to `core/chat/tool_schemas.py:TOOL_SCHEMAS` (names must match). **If the tool is risky** (writes, deletes, external calls), add it to `security/permissions.py`'s `TOOL_RISK_ACTIONS` (§8) — one line per tool, the established pattern for every risky tool added so far.

### 4. Providers (`providers/`)
`BaseProvider` — uniform interface over Ollama (local, default), Claude, OpenAI, Gemini. Each exposes a `base_url` property, used by `security/endpoint_policy.py` (§8) to classify internal vs. external for PII redaction — **classify by the provider's actual configured endpoint, not by name**; `OLLAMA_BASE_URL` is not automatically internal (it points at a WSL virtual-network IP in Docker Compose, or an arbitrary k8s hostname) so "provider is ollama" was a real bug fixed in Fase 1, not a hypothetical. Circuit breaker (Closed→Open→Half-Open) per provider with automatic fallback.

### 5. Memory System (`memory/`)
6 tiers coordinated by `memory_manager.py`: `working_memory.py`, `conversation_memory.py`, `summary_memory.py`, `long_term_memory.py`, `reflection_memory.py`, `vector_memory.py` (pgvector-backed). Exposed via `/api/v1/memory/*`.

**Fase 3 (DCF v5 mandate) wired this up — session-scoped tiers are automatic, cross-session is explicit-opt-in only, never automatic promotion:**
- `memory.memory_manager.get_shared_memory_manager()` is the process-wide singleton — `core/chat/engine.py`, `api/routes/memory.py`, and anything else touching memory MUST use this, not a private `build_memory_manager()` call, or the in-memory (dev/CI) backends end up as disconnected islands that never see each other's writes.
- Every `ChatEngine.stream_run()` turn writes `working` (last files/timestamp) and `conversation` (user + assistant messages) per `session_id`; `summary` refreshes every `MEMORY_SUMMARY_EVERY_N_TURNS` (5) turns. All three are inherently session-scoped — no cross-session/cross-user risk here, and a memory-tier failure only logs a warning, never breaks the chat turn (see `ChatEngine._remember_turn_start`/`_remember_turn_end`).
- Cross-session memory ("mengingat lintas sesi") is two new tools, `remember_fact`/`recall_facts` (`agent/tools/memory_tools.py`), namespaced by **`owner`** (the caller's identity) — deliberately NOT `workspace_id`, since Project Workspaces have multi-user membership and namespacing by workspace would leak one member's remembered facts to every other member. The model calls these only when the user explicitly asks to be remembered — this is intentional, not automatic per-turn promotion (the "promosi memori eksplisit" principle the v5 roadmap required before any cross-session integration). `owner` is injected by `ChatEngine._run_tool` from the session's authenticated caller, same rule already established for `workspace_id` — never trust a model-supplied value for either.
- `vector`/`reflection` tiers are untouched by this pass — `vector` is RAG's concern (§6), `reflection` is the orchestrator's self-improvement mechanism (§2), neither is part of Chat Engine's memory integration.
- **Known limitation**: `remember_fact`/`recall_facts` build a fresh Postgres engine per call when `MEMORY_PERSISTENT_BACKEND=postgres` (same asyncpg-event-loop-affinity constraint `agent/tools/workspace_reader.py` already has) — exercised by hand against a real database, not covered by the unit tests (which only run the in-memory default).

### 6. RAG & Knowledge (`rag/`)
Chunk → embed → store → retrieve → hybrid → rerank → context, exposed via `/api/v1/knowledge/*`. Ingest today is **paste-text only** — no file upload or OCR yet — and the embedder is `hashed_bow_embedder` (offline hash-based, not a production embedding model).

### 7. Workspace (`workspace/`)
Index & scan local folders for agent/RAG use, exposed via `/api/v1/workspace/*`; reading is also available via `agent/tools/workspace_reader.py`.

**Fase 4 (DCF v5 mandate, "Workspace Autonomous Capability") added controlled writes with automatic versioning:**
- `agent/tools/workspace_reader.py::workspace_write_file` (the chat tool) creates/overwrites/appends text files (txt/md/log/csv/json/html) and real PDF/DOCX (mode="overwrite" only for those two). Root Restriction (writing outside the registered folder) is structurally rejected via `tools/tool_validator.resolve_within_root`/`PathEscapesRootError` — this was already true before Fase 4, not new.
- **What Fase 4 actually added**: before any overwrite of a file that already exists, `_write_file` snapshots its current bytes to a new `WorkspaceFileVersion` row (`workspace/versioning.py`) — closes the "silent, unrecoverable overwrite" gap that existed since Tahap 30. The tool result's `action` field is `"created"` / `"overwritten"` / `"appended"` (not a generic echo of `mode`) so the model/user can tell which happened. Every write is also recorded to `security.audit_log` (`workspace.file_written`).
- **Restoring a version is deliberately an HTTP endpoint, not a chat tool** — `GET /api/v1/workspace/{id}/files/{folder_id}/versions` (read, same `_require_member` access as any Workspace content) and `POST .../restore` (mutation, gated on `write_output` same as the write tool). Recovery is a human action via the Workspace UI, not something the model decides mid-conversation. Restoring is itself an overwrite, so it snapshots the current content first too — recoverable recursively, not just the original write.
- **Known, accepted limitation**: this is automatic-snapshot-then-write, not a live pause-and-confirm approval before the overwrite happens. A full in-chat approval flow (new SSE event type, pending-write state, frontend diff UI) was considered and explicitly deferred — Owner chose the smaller slice for this pass. Don't assume a Human Approval gate exists in the chat write path; it doesn't yet.

**Fase 8 (DCF v5 mandate, "Workspace Native File Access & Chat UX Repair"), Slice 1 of a risk-based sequencing (Owner decision, Gate 1) added the reversible half of native filesystem CRUD — delete is a deliberately separate, later slice:**
- Four new chat tools in `agent/tools/workspace_reader.py`: `workspace_find_file` (Smart Search — case-insensitive filename substring match across every Local folder registered to the Workspace, read-only, no `write_output` check), `workspace_create_folder`, `workspace_move_file` (covers both move AND rename — same filesystem operation, one tool, per "no duplicate implementation"), `workspace_copy_file`. The latter three are mutations: gated on `write_output` and actor-stamped, same as `workspace_write_file` already was — `core/chat/engine.py`'s `WORKSPACE_MUTATING_TOOL_NAMES` is the generalized set that check now runs against (was a single `if name == "workspace_write_file"` check before this Fase).
- `tools/adapters/filesystem.py::FilesystemAdapter` gained `exists`/`make_dir`/`move`/`copy`/`search` — every method validates **both** the source and destination through `resolve_within_root` (a caller could otherwise `../`-escape via either argument, not just one). Move/copy onto an existing destination is refused unless the caller passes `overwrite=true`, in which case the destination's previous content is version-snapshotted first (same `WorkspaceFileVersion` mechanism Fase 4 built) — never a silent clobber. **Found by adversarial Gate 2 review, not the original design**: the exists-check-then-act sequence in `_move_or_copy` was a TOCTOU race — two concurrent calls targeting the same not-yet-existing destination could both observe "doesn't exist yet", both skip the version snapshot, and the second write would silently clobber the first with zero recovery, defeating the exact guarantee this mechanism exists for. Fixed with an in-process `asyncio.Lock` per `(workspace_id, folder_id, dst_relative_path)` (`_lock_for` in `agent/tools/workspace_reader.py`) serializing the whole check-then-act block — in-process only, matching this codebase's existing single-process assumption (`ChatEngine.sessions` is an in-memory dict, same posture), not a cross-worker guarantee. Regression test: `test_concurrent_moves_to_same_destination_do_not_silently_clobber`. **Found by a second, formal DCF Gate 2 pass (2026-07-20, independent adversarial subagent review, not the original Fase 8 design)**: `_lock_for` was only ever applied to `_move_or_copy` — `_write_file` (this section) and the Fase 11 auto-save copy (§9/§20) had the *identical* unlocked exists-check-then-act sequence, the same silent-clobber class the fix above claims to close, just not extended to those two call sites. Fixed the same way — both now wrap their check/snapshot/write sequence in `_lock_for`. Verified via a serialization test (forces a yield point inside the critical section, asserts it's never entered twice at once for the same destination) rather than a real concurrent-DB-write race — the shared single-connection SQLite test fixture can't safely model two truly-concurrent transactions, a test-infrastructure limit, not a statement about the Postgres-backed production path.
- **Chat Decision Flow** (`core/chat/engine.py::WORKSPACE_DECISION_FLOW_NOTE`, injected into the user turn whenever a Workspace is bound): steers the model through the mandate's mandatory STEP 1-5 order — path given → resolve against `workspace_list_files`; not found → `workspace_find_file` by name; still not found → ask location; only then → offer upload — and explicitly forbids the "no drive access" / "please upload" refusals before that search has run. This is prompt-level steering, not a hard guarantee (gemma4:e2b can still ignore it on a given turn, no different from any other system-prompt instruction in this codebase) — **but verified live, not just unit-tested**: a real `gemma4:e2b` turn given only a bare filename (no path) correctly called `workspace_list_files` → `workspace_read_file` on the first attempt, summarized the real PDF's actual content, and emitted zero prohibited phrases.
- **Drive access (D:\, E:\, F:\)**: unaffected by this Slice — every function above already works with whatever root path a `WorkspaceFolder` is registered with (Root Restriction generalizes to any root, not just paths under this repo). Making a Windows drive reachable from wherever the process actually runs is a deployment/mount decision (Docker Compose today only bind-mounts `./`, `./reports`, `./uploads` — no Windows drive) that the Owner explicitly deferred (Gate 1) rather than picking a mount strategy now — not something fixed in application code.
- **Delete (file only) — Slice 2, built 2026-07-20.** Folder/recursive delete is still deferred further (see below). **xlsx/pptx — Slice 3, built 2026-07-20** (see §3/§20 for the read/write tools and renderer, and below in this section for the `workspace_write_file` integration). Format-preserving in-place DOCX/PDF edit (today's `workspace_write_file` is still full-replace only for all four document extensions) is Slice 4 — still not built.
- **Workspace Slice 3 (xlsx/pptx, Fase 12) — DCF-classified AUTONOMOUS** (external_dependency MEDIUM/reversible, architecture MEDIUM/reversible — unlike delete, nothing here is irreversible or HUMAN-ONLY), built without an Owner design gate per the "majority of build decisions should be AUTONOMOUS" governance principle. `xlsx`/`pptx` added to `WRITABLE_DOCUMENT_EXTENSIONS` (full-replace only, same as pdf/docx) — `_write_file`'s document branch now dispatches to `write_xlsx`/`write_pptx` (`agent/tools/writers.py`) the same way it already did for `write_pdf`/`write_docx`. `openpyxl` was already a dependency (`api/routes/dokumen.py`'s mining xlsx import path); `python-pptx` is new.

**Workspace Slice 2 (delete, Fase 12) — the DCF decision engine classifies the delete ACT itself HUMAN-ONLY (irreversible); the mechanism to satisfy that was a SHARED design decision Owner made explicitly (4 questions via AskUserQuestion), not something built silently:**
- **Two-step token confirmation** (`workspace/delete_gate.py::WorkspaceDeleteGate`), mirroring `workflows/approval.py::HumanApprovalGate`'s shape (pending state, requester/approver identity recorded, never auto-decides) but scoped for an immediate same-session two-click flow, not an async SLA-tracked queue — no `overdue`/escalation concept, just a short TTL (`DEFAULT_TTL_SECONDS=300`) on the token. `get_shared_delete_gate()` is a process-wide singleton for the same reason `get_shared_memory_manager()`/`get_shared_orchestrator()` already are — the request and confirm calls are two separate HTTP requests, so a fresh instance per call would lose every pending token for the in-memory (dev/CI default) backend.
- **API-only, never a chat tool** (Owner decision) — `POST /{workspace_id}/files/{folder_id}/delete-request` (creates the token, touches nothing on disk, gated on the new `delete_output` permission) and `POST .../delete-confirm` (token + optional reason; re-checks `delete_output` itself rather than trusting the token alone — same defense-in-depth every other mutating route in this file has). Mirrors why `restore` (Fase 4) is also API-only, only more so given delete is more irreversible than restore. **No frontend UI was built for this Slice either** (`restore` already set this precedent — grep confirms zero frontend references to `/versions`/`/restore` today) — both are usable only via direct HTTP calls until a Workspace file-browser UI exists to hang a confirm dialog off of.
- **`delete_output` is owner-only**, not shared with `editor` like every other `WORKSPACE_PERMISSIONS_BY_PROJECT_ROLE` action — the one Workspace mutation classified HUMAN-ONLY gets the narrowest permission tier in the table, a deliberate asymmetry with `write_output` (owner+editor).
- **Snapshot-before-delete, not a true hard delete** (Owner decision) — reuses the exact `WorkspaceFileVersion` mechanism every other Workspace write/restore already has, so a confirmed delete is recoverable via the *existing* restore endpoint. Closer to a soft delete with an extra confirmation gate than an unrecoverable one.
- **File-only this slice** (Owner decision) — `FilesystemAdapter.delete()` refuses directories (`IsADirectoryError`); folder/recursive delete is a separate, higher-blast-radius slice not built yet, consistent with the same risk-based sequencing every other Fase 8 slice used.
- **Token scoping**: a token is bound to the exact `(workspace_id, folder_id, relative_path)` it was issued for — presenting it against a different Workspace/folder 400s, preventing a leaked/misdirected token from being replayed somewhere it wasn't meant for. Single-use by construction (a second confirm with the same token 409s).
- **TOCTOU lock applied proactively this time**, not found by a later adversarial pass — `delete-confirm` reuses the exact same `_lock_for` (`agent/tools/workspace_reader.py`) every other Workspace mutation now uses (§7 above), so a concurrent chat-triggered write and an API-triggered delete of the same file are serialized against each other too, not just against themselves.

**Fase 8 follow-up fix (same day, real-world reproduction) — the prompt-only decision flow above was not enough on its own:**
- **Gap 1, frontend never sent `workspace_id` at all.** `web/src/pages/chat/ChatPage.tsx` had zero Workspace awareness since Tahap 23 first added `ChatRequest.workspace_id` to the backend — the whole chat↔Workspace tool integration (this Fase included) was unreachable from the actual product UI, regardless of backend correctness, because no session ever carried an id to bind. Fixed by wiring the existing `useWorkspaceStore().current` (already set by `WorkspacePage.tsx` on open/create — `workspaceStore.ts`'s own docstring anticipated exactly this future consumer) into `chatService.ts::streamChat`'s request body, plus a small "✓ Workspace terhubung" indicator in `ChatPage.tsx`.
- **Gap 2, prompt steering alone isn't reliable for a small model on a real-size Workspace.** Live reproduction against a real ~114-file Workspace (Windows path given, no exact match visible) showed gemma4:e2b calling `workspace_list_files` (whose JSON dump exceeded `TOOL_RESULT_MAX_CHARS`, silently hiding the match), then calling the *wrong* tool entirely — `read_pdf` on the literal `"D:\..."` string — instead of `workspace_find_file`. Same failure class CLAUDE.md §9 already documents for GIS conversions ("a tiny model ignores tools"), same fix shape: `core/chat/engine.py::ChatEngine._auto_resolve_workspace_file` deterministically extracts a filename from the user's message (`_extract_file_reference`, extension-alternation regex — handles Windows backslash paths, Unix paths, and bare filenames alike) and resolves it server-side via Smart Search + read **before the model's first turn**, injecting the real content (or a "not found"/"multiple matches"/"failed to read" note, explicitly forbidding the model from pretending success) directly into context. Removes the need for the model to correctly sequence tool calls at all for the common single-file case; `WORKSPACE_DECISION_FLOW_NOTE` still guides the remaining cases (browsing, multi-file, explicit tool use).
- **Verified live end-to-end against the exact reported failure**: registered a real Workspace/Project against `/mnt/d/04_Archive` (the WSL-native path for the user's `D:\04_Archive`) — this only works talking to the systemd/WSL-native deployment (port 8001); the Docker deployment (port 8000) still can't see Windows drives at all, per this Fase's original Gate 1 finding, unmounted docker-compose volumes. ### 8. Security (`security/`)
- `auth.py` — `get_current_principal`, API-key principal lookup (`API_KEYS`: comma-separated `key` or `key:role`).
- `permissions.py` — static role→permission RBAC matrix + `TOOL_RISK_ACTIONS` (per-tool risk classification; extend this — one line — when adding a risky tool, see §3).
- `endpoint_policy.py` — `is_internal_endpoint(url)`: loopback / RFC1918 / `.local` / `.internal` / `.svc.cluster.local` = internal, everything else (including blank) = external, fail-closed.
- `prompt_guard.py` / `output_validator.py` / `pii_detector.py` — wired into all three agent paths from §1 as of Fase 1. Behavior differs by path because of streaming: `agents/generic_agent.py` and `agent/core.py` (§3) can block outright on suspicious input and redact PII from output before it's ever returned, since nothing has reached the caller yet. `core/chat/engine.py` (§9) neutralizes-and-continues on input instead of blocking — a live conversation must not go silent on a false positive — and can only detect-and-flag the output after the fact (SSE has already streamed every token by the time the full response is checked), surfaced as a `warning` SSE event, not silently swallowed.
- `audit_log.py` — append-only, hash-chained (`prev_hash`/`entry_hash`, SHA-256, survives rotation via a synthetic marker entry) with size-based rotation (`AUDIT_LOG_MAX_BYTES`/`AUDIT_LOG_BACKUP_COUNT`). Verify integrity independently with `python3 scripts/verify_audit_log.py` — don't trust the log's own contents as proof of its own integrity.
- `startup_validation.py` — `enforce_production_config()`, called from `api/main.py`'s `lifespan`; refuses to start with blank/example/weak credentials when `APP_ENV=production` (no-op otherwise — this deployment currently runs `APP_ENV=development` with loopback-only network binding as the actual isolation mechanism, a deliberate choice, not a gap).
- **Not verified to exist**: a dedicated sandbox for tool-calling/code execution. File-operation risk matrix is partially closed as of Fase 4 — overwrite of an existing Workspace file is versioned + audit-logged (§7), but there's still no live approval pause before it happens (accepted limitation, not an oversight), and delete/rename capability doesn't exist at all (nothing to fix there). Don't enable free-form code execution without checking/building a sandbox first.

### 9. Chat Engine (`core/chat/`) — the primary feature
A ChatGPT-style conversational layer that lets the user read/create/convert files by chatting with the local Gemma model.
- `core/chat/engine.py` — `ChatEngine` runs a streaming tool-calling loop against Ollama `/api/chat` (native function calling). Per turn it: runs `security.prompt_guard`/PII redaction on the input (§8), auto-reads uploaded text files into context, attaches uploaded images as vision input (base64 `images`), streams assistant tokens, and when the model emits `tool_calls` executes them via the shared `ToolRegistry`, feeds results back, and loops (`MAX_TOOL_ROUNDS`). Tools that produce a file (`result["file"]`) surface as downloadable cards. Runs `security.output_validator` on the full accumulated response just before the terminal event (§8). A small deterministic `_fallback` handles GIS conversions if a tiny model ignores tools. Sessions are in-memory (`chat_engine.sessions`, plain dict — no `TaskStore`/`RedisTaskStore`-style abstraction like `task_manager.py` has); swap to Redis later if persistence or horizontal scaling is needed.
- `core/chat/tool_schemas.py` — `TOOL_SCHEMAS`: the curated JSON-schema list of tools exposed to the model. **Names must match registry names.** This is the file to edit when you want the chat to call a new tool.
- `api/routes/chat.py` — `/api/v1/chat/{stream,upload,download,sessions,models}`. `stream` returns Server-Sent Events; each `data:` line is one engine event (`token`/`tool_start`/`tool_result`/`file`/`warning`/`error`/`done`).
- `web/src/pages/chat/` — React chat page (part of the full `web/src/` SPA, §12), parses the SSE stream, renders markdown (`components/chat/ChatMarkdown.tsx`, Fase 10 — see below; this line claimed markdown rendering existed for a while before that was actually true, another instance of the doc-drift this file's opening paragraph warns about) + tool chips + file cards + warning toasts, handles drag-drop upload + model selector.

Files flow: uploads → `uploads/`, generated outputs → `reports/` (downloaded via `/api/v1/chat/download/{filename}`). Path arguments from the model are resolved against `uploads/` then `reports/` by `ChatEngine.resolve_path`, which is what makes multi-step chains (e.g. resize → convert) work.

**Fase 6 (DCF v5 mandate, "Cowork Experience") — chat can trigger a real Orchestrator run.** The mandate's example ("Analisa dokumen ini dan buat laporan" → plan → pick agent(s) → workflow → validate → escalate-if-needed → output) was, before this Fase, only true on the `/api/v1/orchestrator/*` Workflow page — `ChatPage.tsx` had zero awareness of the orchestrator (verified by grep, not assumed). Closed via a new tool, **not** a new SSE protocol:
- `run_orchestrated_workflow(goal, roles, mode)` (`agent/tools/orchestrator_tools.py`) — the model calls this itself (existing tool-calling loop) when it judges a request needs real multi-agent planning rather than one tool call. Runs the real `Orchestrator.run()` via `get_shared_orchestrator()` (§2), returns a structured summary (`final_output`, per-step results, `escalate`, `trace_id`, `state`).
- `ChatEngine._summarize_result()` has a duck-typed branch for this tool's result shape (`"final_output" in result and "escalate" in result`): if `escalate` is true, the summary is the human-readable "needs approval" message, **never** the partial/unvalidated output — the existing `tool_result` SSE event/card renders it exactly like any other tool, no frontend changes needed.
- **If the run escalates**, the chat turn does NOT wait inline — it tells the user to use the **existing** Approval page (`ApprovalPage.tsx`, `/api/v1/orchestrator/approvals/*`) to decide, which works because both paths share `get_shared_orchestrator()`. A live pause-and-confirm inside a chat turn was considered and explicitly rejected (Fase 6 design decision — see `agent/tools/orchestrator_tools.py`'s docstring) in favor of reusing infrastructure that already existed and already worked.
- **Verified live** (not just unit-tested): a real chat message against `gemma4:e2b` correctly called this tool on the first attempt with sensible `roles`/`mode`, and the underlying `research`→`analyst`→`writer` sequential workflow produced a real, substantive report — see the Fase 6 session's verification notes if reproducing.
- **Known limitation**: only `core/chat/` is bridged this way — `agent/core.py` (§3, the older rule-based path) is not, and wasn't asked for.

### 17. Continuous Improvement Engine (`improvement/`) — Fase 7, DCF v5 mandate (final phase)
"AI ENGINE memperbaiki dirinya — namun SELF IMPROVEMENT ≠ SELF UNCONTROLLED CHANGE." Owner explicitly approved the aggressive design (auto-apply + auto-revert, not just analyze-and-recommend) — see `improvement/apply.py`'s module docstring for the full design rationale.

- `improvement/engine.py::ImprovementEngine.analyze()` — pure read, no side effects. Reads `telemetry/metrics.py`'s `error_rate_by_role()`/`total_dispatches_by_role()` (the latter is new — added because a rate alone doesn't tell you if it's statistically meaningful) plus a self-contained `EscalationTracker` (subscribes to the shared orchestrator's `workflow.pending`/`workflow.reviewing` events directly — `MetricsCollector` doesn't track escalation, and this deliberately didn't modify that already-tested module to add it). Detects two categories against configurable thresholds with a minimum sample size (`IMPROVEMENT_MIN_SAMPLES`): workflow escalate-rate out of a healthy band (actionable — maps to a setting) and per-role error rate too high (informational only, `setting=None`, never auto-appliable — no whitelisted fix exists for "this role's prompt needs work").
- `improvement/ledger.py` — append-only, hash-chained (`prev_hash`/`entry_hash`, same SHA-256 technique as `security/audit_log.py`/SEC-8), records every recommendation AND every applied/reviewed action — the append-only property is what makes "AI improves itself" auditable rather than a black box. `verify_chain()`/`pending_actions()` (reconstructs unreviewed actions from the log itself — no separate in-memory queue a restart would lose).
- `improvement/apply.py::WHITELISTED_SETTINGS` — **exactly one** setting this pass may touch: `CONFIDENCE_THRESHOLD_DEFAULT` in `config/agents.yaml`, hard-bounded by `IMPROVEMENT_CONFIDENCE_MIN`/`MAX`, adjusted by `IMPROVEMENT_CONFIDENCE_STEP` per application. A regex line-replace, not a full YAML parse/re-serialize — preserves every comment/other key untouched, so a git diff shows exactly one line changed.
- `improvement/git_ops.py::safe_to_commit()` — refuses to commit if the working tree has ANY uncommitted change other than the exact target file (an autonomous process must never sweep a human's — or this same Claude Code session's — in-progress uncommitted work into its own commit). Every commit/revert is a normal, new commit (`git revert --no-edit`, never `reset`/`--force`/amend) — history is never rewritten.
- `improvement/apply.py::review_pending_actions()` — after `IMPROVEMENT_REVIEW_WINDOW_SECONDS` (default 24h), re-checks whether the original problem persists; if so, `git revert`s the applied commit. **Known, documented limitation**: this is a single post-hoc re-check against the same signal, not a proper controlled A/B comparison — it can't fully isolate causality, just whether the targeted problem still looks bad.
- **`settings.ENABLE_AUTONOMOUS_IMPROVEMENT` defaults to `False`.** Analysis (read-only, safe) always runs every tick regardless — only writing a config change + git commit is gated. Owner approved building the full auto-apply/auto-revert loop as the Fase 7 design, but flipping this on for a real deployment/repo is a further, separate, even more consequential decision than approving the design — not something to default on quietly. Flip it in `config/improvement.yaml` (or `.env`) when ready.
- `improvement/scheduler.py::ImprovementScheduler` — background tick loop (`IMPROVEMENT_TICK_SECONDS`, default hourly), started/stopped in `api/main.py`'s lifespan alongside the existing automation scheduler, but a deliberately separate mechanism (`scheduler/scheduler.py` runs user-created `ScheduledJob` workflows — a different concern).
- Surfaced read-only via `GET /api/v1/monitoring/dashboard`'s new `"improvement"` key (`telemetry/monitoring.py::improvement_dashboard()`) — same `require_role("view_dashboard")` gate as every other dashboard.

### 18. Workspace Manager UI (Fase 9, DCF v5 mandate "Workspace Manager UI — Native Windows Folder Connection")
Slice 1 of a risk-based sequencing (Owner decision, Gate 1): the "Add Folder" flow, Current Workspace status, and chat auto-binding — the mandate's own core "never see workspace_id/WSL path/Docker config" promise. Sidebar tree view, context menus (rename/move/copy/delete), and drag-and-drop are later slices, not built yet.

**The mandate's literal ask — a native OS folder picker driving `registerWorkspace()` automatically — is not something any web app can build.** No browser API (`showDirectoryPicker()`, `<input webkitdirectory>`) ever exposes a real OS path to JavaScript; this is a deliberate browser security boundary, not a gap in this codebase. Same wall blocks "Open in Explorer" — a web page cannot launch the OS file manager. Owner decision (Gate 1, after DCF classified both the picker mechanism and its security surface as SHARED): build an **in-app folder browser** instead (the same pattern Portainer/Synology/etc. use for "pick a folder on the host") — visually similar to a native picker, no path ever typed, and it actually gives the backend a real usable path. "Open in Explorer" is replaced with "Copy Path" (not built this slice — sidebar-tree scope).

- `api/routes/workspace.py::browse_filesystem` (`GET /browse-fs?path=`) — lists immediate subdirectories only (not files: this endpoint exists to pick a *folder*, not browse content). No `path` returns curated starting points (`_browse_roots()`): home directory, any WSL-mounted Windows drives (`/mnt/c`, `/mnt/d`, ...), and `/` as a full-filesystem fallback. Authenticated callers only, no further scoping — Owner decision (Gate 1): "any path reachable from the process" is the intended permission model, same posture Workspace registration already had (permission is the act of picking a folder, not a pre-restricted allow-list).
- `_friendly_path()` — display-only conversion so a WSL path (`/mnt/d/Archive`) renders as `D:\Archive` everywhere the frontend shows a path (browse results, quick-connect response, `/mine` listing) — the mandate's "user never sees the WSL path" requirement. Native Linux/macOS paths pass through unchanged.
- `POST /quick-connect` (`QuickConnectRequest{path, alias?}`) — one call that does everything "Add Folder" needs: creates a Project + Workspace + WorkspaceFolder + runs the initial scan, all via the exact same primitives `create_project`/`create_workspace`/`mount_folder`/`scan_workspace` already use (reuse, not a new system — the mandate's own non-negotiable). Unlike `POST /workspace` (one Workspace per Project, 409 on a second), quick-connect always creates a fresh Project+Workspace pair, since the sidebar is meant to hold multiple independently-connected top-level folders (`D:\04_Archive`, `D:\Projects`, `C:\Users\...\Documents` side by side) — that's the existing 1-Project-to-1-Workspace model, just composed automatically instead of by hand. A scan failure rolls back the whole thing (unlike `scan_workspace`'s existing-workspace-gets-marked-`Error` behavior) since there's no pre-existing workspace worth keeping around empty.
- **Found and fixed while building this**: `workspace.updated_at` (`onupdate=func.now()`) raised `MissingGreenlet` on read immediately after `commit()` — SQLite/aiosqlite doesn't eagerly re-fetch `onupdate` server defaults via RETURNING the way flush()-time INSERT defaults get fetched, so the bare attribute access after commit tried an implicit lazy-load outside any awaited context. Fixed with an explicit `await session.refresh(workspace)` (and `folder`) before building the response dict.
- **Found by adversarial Gate 2 review, not the original design**: `quick_connect`'s scan ran `scan_folders`/`os.walk` directly on the request coroutine — a recursive filesystem walk blocks the WHOLE asyncio event loop, every other API caller, for as long as it takes. `scan_workspace` (existing route) has the identical root cause, but Fase 9 is the first place a casual one/two-click UI affordance (`browse-fs`'s roots deliberately include `/`) makes triggering a full-root scan trivial rather than something an admin has to type by hand. Fixed with `await asyncio.to_thread(scan_folders, ...)` in `quick_connect` — keeps the triggering request itself just as slow, but stops it from stalling every other caller; `scan_workspace`'s pre-existing instance of the same issue was left untouched at the time (out of that Fase's diff, not newly introduced). Also found: `QuickConnectRequest.alias` had no length bound (every other project-name entry point enforces `max_length=256`, matching the `String(256)` DB columns) — added for parity. **Closed 2026-07-20 (formal DCF Gate 2 pass)**: `scan_workspace` turned out easier to self-service-trigger than "something an admin has to type by hand" implied — `quick_connect` requires no elevated role to create a workspace, and `POST /{id}/scan` only requires "admin" on the caller's *own* self-created workspace, so any authenticated user could quick-connect to `/` and freeze the API for everyone by scanning it. Classified SHARED (security domain, MEDIUM risk) via the DCF decision engine, escalated to Owner, approved — `scan_workspace` now uses `asyncio.to_thread(scan_folders, ...)` too, closing the parity gap this section originally left open.
- `GET /mine` — every Workspace the caller can reach (owns or is a Project member of), across Projects, sorted most-recently-updated first — the sidebar's "connected folders" list, populated without the user ever picking a Project. Reuses `api/routes/projects.py::list_projects`'s exact owned-or-member query shape.
- Frontend: `components/workspace/FolderBrowserDialog.tsx` (breadcrumb-style path + click-to-navigate list, backed by `browse-fs`) and `pages/workspace/WorkspaceManagerPage.tsx` — a new **top-level** `/workspace` sidebar area (`app/router.tsx`/`Sidebar.tsx`; a deliberate 12th Information Architecture area, not an oversight of the documented 11), distinct from the older per-Project `pages/projects/WorkspacePage.tsx` (kept untouched for existing workflows). Selecting a folder calls `quickConnect` then `useWorkspaceStore().setCurrent(...)` — the same store `ChatPage.tsx` already reads (Fase 8 follow-up fix) — so chat auto-binds with zero additional wiring. Each connected Workspace also has a Disconnect (`Unlink` icon) action wired to the existing `DELETE /{workspace_id}` soft-delete — the mandate's "memutuskan koneksi Workspace" requirement, missed in the initial pass and added right after.
- **Known Slice 1 simplification**: the Current Workspace status panel's file count comes from the connecting/last-rescan's scan result, held in local component state — not continuously live. A full "folder moved/deleted → Reconnect" flow (rebinding the *same* Workspace id to a new path) is deferred to a later slice; for now, switching to a Workspace re-runs its scan (which flips `status` to `"Error"` server-side if the path is gone, surfaced via a badge + a prompt to Add Folder again) as a lightweight substitute.

### 19. Chat Markdown Rendering (Fase 10 fix)
`prompts/chat/system_v1.md` has always instructed the model to "pakai heading, poin, dan tabel markdown" — but `web/src/components/chat/MessageList.tsx` had no Markdown parser at all, ever: it dumped `message.content` as plain text (`white-space: pre-wrap`), so every `### **Heading**`, bullet, and table the model produced showed up as literal raw syntax in the chat bubble instead of being rendered. Not a regression — this had simply never been true, another instance of the doc-vs-code drift this file's opening paragraph warns about (§9's own line claiming "renders markdown" predates this fix).
- `web/src/components/chat/ChatMarkdown.tsx` — `react-markdown` + `remark-gfm` (GFM adds table/strikethrough/task-list support, needed since the system prompt explicitly asks for tables), with compact custom component overrides (small heading sizes, tight spacing, `overflow-x-auto` code blocks/tables) so it fits the existing chat-bubble aesthetic instead of default browser heading sizes. Deliberately **no** `rehype-raw`/raw-HTML pass-through — model output is untrusted text, and react-markdown's default (Markdown syntax only, never executes embedded HTML/`<script>`) is what keeps this XSS-safe by construction; verified with a test asserting a `<script>` tag in model output never reaches the DOM.
- Wired into `MessageList.tsx` for **assistant** messages only — the user's own typed bubble stays plain text (unchanged), so a user typing a literal `*` or `#` never gets silently reinterpreted as Markdown.
- Tests: `web/tests/components/ChatMarkdown.test.tsx` (heading+bold combo renders as real elements not literal `###`/`**` text, GFM tables render, bullet lists render, raw HTML never passes through).

### 20. Generated-Document Formatting + Workspace Auto-Save (Fase 11 fix)
Two bugs reported together from real usage: DOCX output was "berantakan" (messy), and a generated file landed only in `~/ai_engine/reports/` even with a Workspace connected — the user had to download it and re-upload it into their project folder by hand.

- **Formatting**: `agent/tools/writers.py::write_docx`/`write_pdf` used to hand-parse content line by line (prefix-match `"# "`/`"## "`, `line.split("**")` for bold) — the same class of bug §19 already found and fixed on the chat side, just never closed here. It never handled numbered lists, GFM tables, or nested formatting inside a heading at all, so `### **Ringkasan**` produced a docx heading whose actual text was the literal string `**Ringkasan**`, and any markdown table the model wrote (the system prompt explicitly asks for tables) came out as raw `| pipe | text |` paragraphs. `core/document/markdown_render.py` is the fix: one `markdown-it-py` (CommonMark + GFM tables) parse into a small `Block`/`Run` intermediate representation, with two renderers — `render_docx_body()` (python-docx: real Heading 1-4/List Bullet/List Number/Light Grid Accent 1 table styles) and `render_pdf_story()` (ReportLab flowables) — so there's exactly one place that understands Markdown feeding both formats, not two hand-rolled parsers drifting apart. Same architecture as §19's frontend fix, Python-ecosystem equivalent.
- **Workspace auto-save**: `write_docx`/`write_pdf`/etc. are general-purpose writers, unaware of any connected Workspace by design (unlike `workspace_write_file`) — the model calling one of these instead of the Workspace-aware tool when a Workspace is connected is the same small-model tool-selection unreliability `_auto_resolve_workspace_file` (Fase 8 follow-up) already worked around for reads. `core/chat/engine.py::_run_tool` now auto-copies the result of any `REPORT_WRITER_TOOL_NAMES` call into the connected Workspace's first Local folder afterward (`agent/tools/workspace_reader.py::_copy_generated_file_into_workspace` — same `WorkspaceFileVersion` snapshot-before-overwrite guarantee as every other Workspace write) rather than relying on the model choosing the right tool up front. The tool result gains `workspace_saved_path`/`workspace_folder_id` (or `workspace_save_error` on failure, without turning a successful report generation into a failure) so the model's response can say where it landed.
- **Found while verifying this live, not in the original design**: the Fase 8 follow-up's `_auto_resolve_workspace_file` — built for READ turns — also fired on CREATE turns, since a message like "Buatkan file docx bernama laporan.docx" mentions a filename with a recognized extension too. It searched for the not-yet-created file, found nothing, and injected a "TIDAK ditemukan ... JANGAN pura-pura sudah membaca file ini" note into what was actually a creation request — visibly garbling the model's response. Fixed with `_CREATE_INTENT_RE` (buat/bikin/create/generate/tulis/susun and Indonesian variants) — any creation-intent verb skips auto-resolve entirely for that turn, falling back to the model's own tool calls (same reliability as before Fase 8, never worse, just not bootstrapped).
- **Verified live, not just unit-tested**: asked the real chat (`gemma4:e2b`) to create a docx with headings/bullets/a table while a real Workspace was connected — the response opened with `✓ File berhasil dibuat di Workspace`, the tool result read `File dibuat: ... (juga disimpan ke Workspace: ...)`, and the actual file on disk had real Heading/List Bullet/table structures with zero literal `###`/`**`/`|` anywhere.
- **Three gaps found and closed by a formal DCF Gate 2 pass (2026-07-20, independent adversarial subagent review of this whole Fase, not the original design):**
  1. **Security, CONFIRMED HIGH, classified SHARED and escalated to Owner (approved)**: the auto-save path above had **no `write_output` permission check at all** — unlike the four dedicated `WORKSPACE_MUTATING_TOOL_NAMES` tools, which are gated on it. A Project member with only `viewer`/`read` (enough to bind `workspace_id` to a chat session at all) could get any `REPORT_WRITER_TOOL_NAMES` tool to silently plant a file in the connected Workspace's real folder, completely bypassing the write-permission model Fase 4/8 built. Fixed: `_run_tool` now calls `require_workspace_permission(workspace_role, "write_output")` before the copy, same as the mutating tools; a denial degrades to `workspace_save_error` (the report itself still generated fine) rather than failing the whole tool call.
  2. **Correctness, CONFIRMED**: `_CREATE_INTENT_RE.search(text)` scanned the *whole message*, not just the text governing the extracted filename — so a mixed-intent turn like "Buatkan ringkasan dari file X.pdf" (a READ of X.pdf, producing an unnamed new summary) also matched "Buatkan" and disabled auto-resolve entirely, regressing the exact live-verified scenario two bullets above. Fixed in `_extract_file_reference`: a creation verb only disables auto-resolve when it governs the matched filename directly (nothing but the verb and a few words between them) — a source preposition ("dari"/"from"/"of") between the verb and the filename means the file is being read, not created, and auto-resolve still fires.
  3. **Robustness, CONFIRMED**: the writer's `registry.execute()` call and the workspace-copy step shared one `try`/`except`, so an *unhandled exception* during the copy (not just a returned `{"success": False}`) would propagate into `_run_tool`'s outer exception handler and discard an already-successful write result entirely, contradicting the "never turn a successful generation into a reported failure" guarantee this section claims. Fixed by isolating the copy step in its own `try`/`except`, degrading to `workspace_save_error` on any exception.
- **`core/document/markdown_render.py` gaps found by the same Gate 2 pass, all AUTONOMOUS fixes (reversible, in-scope, low risk — no Owner escalation needed)**: nested list items were silently *dropped entirely* (not just unindented) — `Block.items` now carries `(depth, runs)` per item and both renderers indent rather than discard; Markdown images produced zero output with no fallback — now render as a `[Gambar: alt text]` placeholder run, same "plain text, not the real thing" treatment already given to links; the PDF renderer collapsed every heading level ≥2 into one style (DOCX kept Heading 1-4 distinct) — PDF now derives progressively smaller H3/H4 styles from `h2` instead of adding new required style keys; the PDF renderer also ignored a markdown ordered list's custom start number (`3. foo` always rendered as `1.`) — now reads `Block.start` from the `ordered_list_open` token.
- **Extended to xlsx/pptx (Workspace Slice 3, Fase 12)**: `render_xlsx_workbook()`/`render_pptx_slides()` reuse the exact same `parse_markdown()` Block/Run IR the docx/pdf renderers already used — still "one parse feeding every renderer," now four instead of two. A shared `_group_by_top_heading()` helper splits the block list at every H1: each H1 starts a new sheet/slide, content before the first H1 (or the whole document, if there's no H1) lands under the caller's `title`/`default_title`. GFM tables become real multi-column sheet rows (xlsx) or a separate "Title Only" slide with a real pptx table shape (pptx, since mixing a table into a bulleted body placeholder isn't a sensible layout) — everything else (headings/paragraphs/lists) becomes single-cell rows / bullet lines, reasonable for "generate a data table with commentary" but not a general-purpose docx-to-xlsx/pptx converter. `agent/tools/writers.py::write_xlsx`/`write_pptx` take the same `{filename, title, content}` shape as `write_docx`/`write_pdf`; `agent/tools/readers.py::read_xlsx`/`read_pptx` return per-sheet/per-slide text previews, same `{source, type, text, ...}` shape every other reader uses.

## Deployment

Three active deployment modes:
| Mode | Port | How |
|---|---|---|
| Docker Compose | 8000 | `docker compose up -d` |
| systemd (WSL) | 8001 | `ai-engine.service` auto-starts on boot |
| Kubernetes | — | `kubectl apply -k k8s/base` (+ overlay `production`); Kustomize base + overlay, verified live in local `kind` |

Postgres/Redis/API/RQ-dashboard ports are bound to `127.0.0.1` only in `docker-compose.yml` (loopback-only network isolation, not to be removed casually — see §8 Security).

Ollama runs on the host at `http://172.29.239.93:11434` (WSL host IP). The default model is `gemma4:e2b` (7.2 GB, fast). `gemma4:26b` is available for formal reports.

Output files go to `reports/`, uploaded files land in `uploads/`. Both are volume-mounted in Docker.

## Key Configuration (`.env` + `config/*.yaml`)
Most `Settings` field defaults now live in `config/*.yaml` (Configuration Center, versioned); `.env` stays for secrets and per-deployment overrides.
- `OLLAMA_BASE_URL` — point to Ollama instance (host or Azure VM)
- `GEMMA_MODEL` — active model (`gemma4:e2b` default)
- `DATABASE_URL` — asyncpg connection string
- `REDIS_URL` / `REDIS_PASSWORD` — broker + cache; `REDIS_PASSWORD` is required by `docker-compose.yml` (`redis --requirepass`), generate a real value, don't leave it as the placeholder
- `API_KEYS` — comma-separated `key` or `key:role` for `security.auth.get_current_principal`; blank (dev default) means every checked route treats the caller as admin — see CLAUDE.md Architecture §1/§8
- `AI_CACHE_TTL` / `GIS_CACHE_TTL` — Redis TTLs for AI and GIS responses
